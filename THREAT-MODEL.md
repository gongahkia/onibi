# Threat model

Onibi grants a paired browser control over existing Ghostty terminals. It acts with the local OS user's authority. The Mac, Ghostty, the configured multiplexer, and their processes are trusted. A paired client can execute commands and terminate work.

The web server binds only to loopback. For remote use, Tailscale Serve terminates private HTTPS and forwards to the local listener. Tailscale, the tailnet access policy, the browser, and the Mac's local network stack are trusted parts of that route.

The managed-session daemon (run by `onibi web` unless one is already running, or alone by `onibi start`) listens only on the same-user intake socket. When it runs, the paired web cockpit reaches it through that socket, so a paired browser can start a shell or any program in a folder it names, and read, type into, interrupt and end those sessions. This adds no capability beyond typing into a Ghostty pane, which a paired browser can already do. It cannot adopt multiplexer sessions that Onibi did not start. See [managed sessions](docs/managed-sessions.md).

## Protections

- Browser pairing uses a random, single-use secret that expires after ten minutes. Temporary access expires after twelve hours or restart. An explicit remembered-browser choice grants a fixed 30 days with an origin-scoped credential hash stored on the Mac. Remote cookies are Secure, HttpOnly and SameSite Strict. Only GET session recovery can exchange a remembered credential for a fresh session/CSRF token; expired writes are rejected. Names are unverified labels. Secrets are stripped from the URL fragment before asynchronous work.
- Each request checks the device grant. Commands recheck after waiting for execution and again after native target validation. Individual revocation ends all sessions for that device and prevents remembered renewal. Local `onibi web devices revoke-all` also invalidates the unused pairing grant. The 0600 administration socket verifies same-user peers and exposes only pairing/device management; background service logs omit pairing links.
- Web requests require the configured Host/Origin and state-changing requests require a session CSRF token. Loopback proxy hosts are explicitly configured; forwarded headers do not establish trust. There is no public listener or CORS API.
- Web actions claim a durable receipt before execution. Replays return that receipt; crashes leave uncertain actions for inspection. Input text is not persisted in receipts. Restart recovery requires an exclusive state-directory lock.
- Native actions use Ghostty process and surface identities rather than terminal titles or positions. Output capture checks the focused pane before and after reading bounded Accessibility text. Pane/tab/window closure binds confirmation to the exact reviewed pane IDs; the server and native bridge both reject changed membership. Bounded follow-up observations distinguish removal, continued presence, and an unverified outcome without replaying the close. Layout and title controls come from a fixed server allowlist and require a verified focused pane; arbitrary native action strings are not exposed.
- Passive diagnostics inspect app/process metadata and Accessibility trust without native Apple events or terminal reads. The HTTP health endpoint requires pairing. Explicit CLI probes may request Automation access. Health observations are historical; version capabilities do not prove current permission or responsiveness.
- Concurrent inventory polling shares only in-flight work and backs off after failure. Mutations bypass polling backoff and validate fresh native targets; no cached list authorizes input. Capture and native availability are tracked separately so an HTTP response or successful read cannot clear a failed inventory observation in the phone interface.
- Managed-session actions use the same receipts, grant rechecks and CSRF checks as Ghostty actions. The server confirms the session in a fresh daemon listing before dispatch, and the daemon accepts only the full session ID from web requests, never a name or prefix match. Ending a session requires a confirmation naming it. Captured colours are parsed into inert text runs; other terminal escape sequences are dropped.
- Push notifications are opt-in per browser and stored against that browser's grant; revoking or expiring the grant stops them. The server posts only to the HTTPS endpoints of the browser vendors' push services (Apple, Google, Mozilla, Microsoft), never to an arbitrary URL a browser supplies, and does not follow redirects. Payloads are encrypted for the subscribing browser (RFC 8291) and contain the session name and a generic reason such as "Yes/no prompt", never terminal output. The VAPID signing key lives in the state database.
- Local state and uploaded files use restrictive filesystem permissions. The intake socket is same-user only and accepts only session control requests. Opening a state database from an earlier release drops its stored tool approvals and Claude questions.

## Residual risks

- The push service learns when a notification is sent and to which browser, and the phone's lock screen shows the session name. Use session names you are comfortable seeing there, or leave notifications off.

- A leaked unused browser pairing link, session, or remembered credential grants terminal control. Remembered credentials can restore access until their fixed expiry unless revoked. Use local device revocation, or stop the web process to cut off control while stopped. Restart does not erase remembered grants. A compromised same-origin page can act with the browser’s authority despite HttpOnly cookies.
- Focus and output capture span separate operating-system calls; they cannot form one atomic Ghostty transaction. The adapter discards detected focus changes, but cannot prove no focus change occurred and reversed between checks. Output is visible plaintext, not full terminal history.
- Focus-dependent layout/title actions also span separate operating-system calls. A concurrent focus change can race the final check; these calls are not atomic with local interaction.
- Follow reads bounded text only while visible and never automatically focuses a pane. Drafts are per-pane and memory-only, as is the recent sends and copies list; terminal output remains inert text. Only font/wrap preferences persist in local storage. Explicit copying writes terminal text to the system clipboard, outside Onibi’s retention control.
- Closing a Ghostty pane, tab, or window may terminate its processes. Membership checks and the close are separate native calls; local changes can race the final check. Observed disappearance verifies reviewed panes, not an empty window object or a program’s clean shutdown. An already executing action can finish during logout or shutdown; revocation cannot undo input already sent.
- Local processes running as the same OS user may read Onibi state or control the multiplexer directly. Onibi does not sandbox commands or protect against a compromised host.
- Managed-session reads include up to 2,000 lines of scrollback, which may hold secrets that have scrolled off screen. Attention states are heuristics over screen text and can miss or misreport a prompt.
- Adopting an existing mux session gives Onibi, and any paired browser while the daemon runs, the ability to send input and kill that session. Existing Pi/Claude processes do not gain hooks merely by being adopted.
- Onibi launches agents plainly and adds no hooks, so their own terminal prompts remain the only approval path. Programs reached through the phone run with the Mac user's privileges and whatever permission mode they were started with.

Use a non-production OS account for evaluation.
